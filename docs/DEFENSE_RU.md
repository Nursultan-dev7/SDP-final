# Подготовка к защите Blockchain Wallet

## Демонстрация за 4–5 минут

1. Запустить `run.cmd`. Объяснить: Java Swing, локальный симулятор, Alice = 100 DCO, Bob = 0 DCO. Никаких реальных средств и внешней сети.
2. Ввести 30.00, Standard → Review: комиссия 1.00. Отменить; выбрать Priority → Review: комиссия 3.00, итог 33.00. Показать Strategy и создание Transaction через Builder.
3. PIN `2468`, неверный код → отправка отклонена, история пустая, баланс 100.00. Показать, что AuthenticatedSender реализует TransferSender и оборачивает другой TransferSender: это Decorator.
4. Ввести отображаемый demo code → Pending. Available = 67.00, Confirmed = 100.00. Adapter переводит BigDecimal DCO в long minor units, UUID в string и числовые статусы узла в enum.
5. Create block → Confirmed, Alice = 67.00, Bob = 30.00, комиссия 3.00 удалена из demo supply. Observer обновляет TransactionHistory по событию узла. Facade объединяет сценарий для UI.
6. Запустить `test.cmd` или `java -jar build/BlockchainWallet.jar --test`. Показать регрессионные проверки expiry, replay и отказа подписчика. Показать UML, Git-историю и собственные два паттерна каждого участника.

## Шесть паттернов

| Паттерн | Тип | Что показать и почему нужен |
| --- | --- | --- |
| Builder | Creational | `TransactionBuilder`: пошаговая сборка immutable record; канонический конструктор защищает инварианты при любом способе создания |
| Strategy | Behavioral | `StandardFeeStrategy/Priority`: взаимозаменяемые алгоритмы комиссии; контекст получает стратегию, а не выбирает алгоритм условными операторами |
| Decorator | Structural | `AuthenticatedSender(delegate, authenticator)` и `NetworkSender` реализуют общий TransferSender; декоратор добавляет проверку перед делегированием |
| Adapter | Structural | `LocalChainAdapter implements WalletNetwork`: приводит несовместимый формат LocalChainNode к контракту кошелька, включая события |
| Observer | Behavioral | `onIncluded` → адаптер → `history::onConfirmation`; издатель не знает конкретного класса истории |
| Facade | Structural | `WalletFacade`: UI вызывает prepare/submit/balances/history/createBlock, не организуя взаимодействия низкоуровневых компонентов |

## OOP: короткие ответы

- **Инкапсуляция:** баланс, pool и challenge скрыты в private-полях; изменяются методами, поддерживающими правила модели. Immutable Transaction не раскрывает изменяемое состояние.
- **Абстракция:** WalletNetwork, FeeStrategy, TransferSender и TransferAuthenticator описывают контракты без деталей реализации.
- **Полиморфизм:** calculate вызывается через FeeStrategy, а Java выбирает реализацию Standard/Priority. Sender также вызывается через интерфейс.
- **Наследование и композиция:** WalletPanel наследует JPanel, стратегии реализуют интерфейс, AuthenticatedSender содержит delegate. Decorator расширяет поведение через композицию.
- **Почему record:** значения полей неизменяемы, автоматически получаем equals/hashCode/accessors. Для этого record поля тоже неизменяемых типов. Record сам по себе не валидирует вход — для этого добавлен compact constructor.
- **Почему BigDecimal/long, а не double:** десятичные суммы должны сохранять точность. UI и модель используют BigDecimal, узел — целые minor units. Округление HALF_UP применяется только при расчёте процентной комиссии; недопустимые доли minor unit у транзакции отклоняются.
- **Почему abstract class не нужна:** у стратегий нет необходимого общего изменяемого состояния; интерфейса достаточно.

## SOLID на конкретных классах

- **S:** WalletPanel — UI; DemoAuthenticator — challenge; LocalChainNode — ledger; TransactionHistory — история. Facade отвечает за координацию сценариев, Main — за сборку.
- **O:** новый алгоритм комиссии реализует FeeStrategy; существующие алгоритмы не меняются. Для выбора нового алгоритма в UI нужно зарегистрировать пункт меню.
- **L:** обе реализации TransferSender сохраняют контракт отправки/возврата Receipt и допустимых ошибок валидации; Decorator добавляет авторизацию. Не утверждать, что замена гарантирует успешную отправку при любых credentials.
- **I:** узкие контракты стратегий, отправки и авторизации отделены от Swing и конкретного узла.
- **D:** Facade зависит от WalletNetwork/TransferAuthenticator, Decorator — от TransferSender/TransferAuthenticator. Конкретные зависимости выбираются в Main.
- **DRY:** Builder и прямой конструктор используют одну точку валидации Transaction; UI не дублирует логику комиссий и списания.
- **KISS:** стандартная библиотека, небольшой локальный ledger, минимальный набор зависимостей. Не добавлять паттерны ради количества.

## Вопросы, на которых легко ошибиться

- **Adapter vs Facade:** Adapter делает формат существующего узла совместимым с контрактом; Facade упрощает выполнение нескольких операций для клиента.
- **Decorator vs Strategy:** Decorator оборачивает объект с тем же интерфейсом и добавляет поведение; Strategy заменяет алгоритм в контексте.
- **Observer vs прямой вызов истории:** узел хранит callbacks и не зависит от TransactionHistory; можно добавить другого подписчика. События здесь синхронные, не очередь сообщений.
- **Почему 67, а не 70:** перевод 30 + комиссия 3. Пока Pending, 33 зарезервированы; при майнинге списываются с confirmed.
- **Почему priority не обязательно подтвердится раньше другого блока:** один блок включает все текущие pending; стратегия влияет на порядок внутри блока, не на гарантированную задержку внешней сети.
- **Что если подписчик бросит исключение:** ledger уже зафиксирован; ошибка логируется, другие подписчики получают события. Повторной доставки отказавшему подписчику нет — это ограничение демо.
- **Это настоящая MFA?** Нет. Код в том же окне демонстрирует поток проверки, но не независимый второй фактор. PIN захардкожен для учебного запуска.
- **Что с многопоточностью:** UI вызывает ledger на Swing EDT; классы не предназначены для параллельного серверного использования.
- **Почему это blockchain simulation:** блоки содержат предыдущий hash и вычисленный SHA-256; нет распределённого консенсуса, цифровых подписей и proof-of-work.
- **Дальнейшая работа:** персистентность, подписи, хранилище ключей, независимая авторизация, тестовая внешняя сеть, доставка событий с восстановлением.

Перед защитой каждый участник должен уметь объяснить весь transfer lifecycle и подробно показать собственные два реализованных паттерна с реальными коммитами.

## Иерархия для показа преподавателю

В src/wallet находится только Main.java. Шесть подпакетов: builder, strategy, decorator, adapter, observer, facade. Пакет совпадает с путём исходного файла; каждый самостоятельный тип в отдельном файле. Main собирает конкретные компоненты и в режиме --test запускает проверки всех паттернов. Тестовые классы находятся в tests/wallet/facade и используют существующий пакет facade. Команда python docs/verify_structure.py проверяет также JAR и актуальность исходного ZIP.
